# 네이버 카페 공고 수집 파이프라인

대상: 카페 `제주도 게스트하우스 여행자모임`(cafeId 22960569) · 게시판 `G.H.스탭모집방-제주`(menuId 142)

## 0. 하루 흐름 ("스탭핑 오늘 크롤링 시작해")

```bash
node scripts/crawl-naver-cafe.mjs --pages=1 --size=30   # 새 글 수집 + 파싱 + 검수 대기 목록
node scripts/read-image.mjs <글번호> <시트번호...>      # 안내문 이미지를 읽기 좋게 분할 (Claude가 읽는다)
node scripts/import-crawled-jobs.mjs --dry-run          # DB 업로드 미리보기 (신규/갱신/썸네일 수)
node scripts/import-crawled-jobs.mjs                    # 오늘 처음 올라온 글을 Supabase 에 업로드 → 배포 사이트에 노출
node scripts/lib/parse-cafe-post.check.mjs              # 파서 회귀 체크
```

1. **수집/파싱**: 새 글만 `.crawl/raw/`에 캐시하고, 전체를 다시 파싱해 `.crawl/posts.json`, `.crawl/review.json`을 만든다. 이미지는 `.crawl/sheets/<글번호>.jpg`(앞 12장 번호 시트)로 묶어둔다.
2. **Claude 검수** (API 키 불필요, Claude가 이미지를 직접 읽는다)
   - 시트를 보고 **썸네일 번호**를 정해 `.crawl/thumb/<글번호>.txt`에 기록 (`none`이면 기본 이미지).
   - 시트에 **안내문/공고문 이미지**가 있으면 `read-image.mjs`로 잘라 읽고 `.crawl/ocr/<글번호>.txt`에 전사. 없으면 빈 파일. 전사 텍스트는 같은 파서로 재해석된다.
   - **어필 포인트 요약**: 글을 끝까지 읽고 `.crawl/summary/<글번호>.json`에 `{ intro, highlights:[{title, items[]}] }`로 정리한다(복지·근무와 하루 일과·분위기·위치·선호 인재·모집 안내). 연락처는 넣지 않는다. 상세의 "모집 정보"에 그대로 보인다(마이그레이션 `020`).
   - 파서가 틀리게 읽은 값은 같은 파일의 `fields`(컬럼 이름 그대로), `apply`, `party_kind`로 덮어쓴다. 업로드 때 반영된다.
   - 목록은 페이지가 여러 장이므로 어제·오늘 글을 다 받으려면 `--pages=4 --size=30`으로 돌린다. 업로드는 `--days=2`.
3. 스크립트를 다시 돌리면(캐시라 몇 초) 보강된 결과로 갱신된다. **그래도 비는 필드는 Claude가 목록으로 정리해 사장님께 알리고, 사장님이 직접 판정해서 넘긴다.**
4. **업로드**: `import-crawled-jobs.mjs`가 대표 글을 `crawled_job_posts`에 올리고 썸네일을 4:3으로 잘라 `crawled-job-images` 버킷에 저장한다. 같은 글(끌올)은 `source_group_id`로 찾아 갱신하고, 숨김 처리한 글의 `status`는 덮어쓰지 않는다.

- 목록 API는 로그인 없이 가능, **본문은 로그인 쿠키 필요** (`.env.local`의 `NAVER_NID_AUT`, `NAVER_NID_SES`). 만료되면 재발급.
- 글 사이 0.8초 간격 유지(차단 방지). 이미 받은 글은 건너뜀. `.crawl/`은 gitignore.

기준: `JobPostForm`, `GuesthouseForm`, `docs/database-spec.md`. 해석률은 30건 기준으로, **글에서 직접 읽어낸 비율**이다(기본값 가정 제외).

| recruit_count | O | `모집인원`, `남2 여2`, `N명 모집` | 27% | `1` 가정 |

## 2. 파티와 포틀럭

| party_kind | 의미 | has_party | 태그 |
|---|---|---|---|
| `party` | 술/클럽식 파티 | `true` | 파티있음 |
| `potluck` | 음식 나눠 먹는 잔잔한 모임 | `false` | 포틀럭 |
| `none` | 명시적으로 없음 | `false` | 파티없음 |
| `null` | 언급 없음/불명 | `false` | - |

- 필터 "파티 있음"은 `party`만 걸린다. 포틀럭은 필터에 안 걸리고 `party_description`과 태그로만 보인다.
- 포틀럭이 나온 글에서는 맥주·칵테일·클럽·`파티게하`·대형 파티 같은 **강한 단서**가 있을 때만 `party`로 본다. 포틀럭 글의 "저녁 파티 준비"는 포틀럭이다.
- "근처/주변/제휴업체" 문장은 우리 숙소 얘기가 아니라서 판정에서 제외한다.
- 부정 표현("파티는 없습니다", "파티하는 게스트하우스가 아닙니다")이 한 줄이라도 있으면 `none`이 우선한다.

## 3. 썸네일 판단 규칙

**구조**: 목록 카드(4:3 `object-cover`)는 `guesthouse_photos`의 sort_order 0 → 없으면 `job_post_photos` 첫 장 → 없으면 기본 이미지를 쓴다. 상세 상단 슬라이더는 게하 사진, `모집 정보` 갤러리는 모집글 사진이다. 최대 5장·5MB·JPG/PNG/WEBP. **그래서 썸네일은 `guesthouse_photos`의 0번으로 넣는다.**

**1단계 · 자동 하드 규칙** (`pick-thumbnail.mjs`, 시트에 사유가 빨간색으로 표시됨): 본문 사진(`se-image-resource`)만 · JPG/PNG/WEBP · 5MB 이하 · 가로 600px 이상 · 가로/세로 0.7~2.0 · 흰 배경/색 종류가 적은 글자판 의심 제외. 앞 8장에서 가로형 우선으로 자동 1차 선택.

**2단계 · 눈으로 보는 내용 규칙** (Claude가 시트를 보고 번호 선택, 자동 선택보다 우선):

| 순위 | 채택 |
|---|---|
| 1 | 숙소 외관 · 전경 · 오션뷰 · 마당 |
| 2 | 공용공간(라운지·주방·바) |
| 3 | 객실 |
| 4 | 단체사진 중 얼굴이 작고 장소가 보이는 것 |

- 일하는 곳이 숙소가 아니면(바·카페·책방) 그 일터 내부를 1순위로 본다.
- 외관이라도 간판 클로즈업처럼 일부만 잘린 건 공용공간보다 낮게 본다.
- **제외**: 안내문·포스터·브랜드 배너(글자가 큰 것) · 카톡/인스타/지도/메뉴 캡처 · 포토부스 · 음식·음료만 · 동물 클로즈업 · 얼굴 클로즈업/셀카 · 화장실·냉장고·침구 클로즈업 · 어두워서 장소를 알 수 없는 야간 사진 · 흐림/저화질 · 연락처·QR 노출.
- 세로 사진은 4:3 중앙 크롭(세로의 약 56%만 남음)에서도 피사체가 유지될 때만 쓴다.
- 적합한 게 없으면 `none` → 기본 이미지. 사진이 아예 없는 글(30건 중 3건)도 같다.
- 사진 수 기준 규칙 검증: 10건을 직접 판정했고, 자동 규칙만으로는 "포토부스 컷", "동물 사진", "야간 단체사진"을 걸러내지 못해 눈 판정이 필요했다.

**등록 시 처리 (아직 미구현)**: 네이버 CDN 이미지를 우리 버킷에 재업로드하고, 썸네일은 `sharp`의 `fit: "cover", position: "attention"`으로 4:3 크롭해서 저장한다.

## 4. 안내문 이미지 읽기 (OCR)

- API 키 없이 **Claude가 이미지를 직접 읽는다.** `ANTHROPIC_API_KEY`는 필요 없다.
- 흐름: 본문에서 못 채운 필드가 있고 이미지가 있는 글 → 시트(`.crawl/sheets/<글번호>.jpg`)에서 안내문/공고문 이미지 번호를 찾고 → `read-image.mjs`로 읽기 좋게 분할 → Claude가 읽어 `.crawl/ocr/<글번호>.txt`에 전사 → 재파싱하면 같은 파서가 필드를 채운다. 전사 텍스트 속 번호도 지원 안내에 반영된다.
- 이 단계는 스크립트가 자동으로 하지 않고, **"오늘 크롤링 시작해" 세션에서 Claude가 수행**한다.
- 긴 세로 이미지는 가로 1000px, 세로 1.4배 단위로 분할한다. 12장 뒤 사진은 `sheet.mjs <글번호> <시작번호>`로 본다.
- 비율로 안내문을 추정하지 않는다(휴대폰 세로 사진을 안내문으로 오인). 시트를 보고 판단한다.
- **현황**: 지금까지 46건 중 본문이 600자 미만인 이미지 위주 글은 2건이었고, 시트로 확인한 21건에서 안내문 이미지는 **0건**이었다. 근무 정보는 거의 다 본문 텍스트(하루 일과표 포함)에 있다. 첨부파일(PDF)이 있는 글도 아직 없다(목록 50건 중 `hasFile` 0).
- **미지원**: 카페 첨부 PDF. 나타나면 파일을 받아 같은 방식으로 읽는 단계를 추가해야 한다.

## 5. 지원 방법과 연락처 (결정: 번호는 지원 안내에만 보여준다)

지원 안내는 본문에 있다. 46건 전수 대조 후 분포: 문자/전화 29 · 카톡 10 · 메일 3 · 인스타 DM 2 · 오픈채팅 1 · 원문 확인 1(글에 지원 정보 없음).

**채널은 후보별 점수로 고른다**(메일 · 인스타 · 카톡 · 문자). 전수 대조에서 이런 경우가 나와서 규칙을 넣었다.
- "문자, SNS, 카톡등으로 지원 받지 않습니다 / 메일 지원" → 거절된 채널은 제외하고 메일. 문의용 번호는 연락처로만 보여준다.
- `접수처: …@…` 이메일 접수 + 문의용 번호 → 메일이 주 경로.
- 한 글에 지점별 번호가 둘(애월주택/푸른하우스) → 버튼 없이 번호 목록 + 원문 안내.
- 카카오톡 채널 링크(`pf.kakao.com`)는 카드 형태라 본문 텍스트에 없고 `href`에만 있다 → 원본 HTML에서 따로 추출.

- 연락처는 "지원 방법" 헤더 아래가 아니라 글 맨 끝, 주소 줄, 헤더에서 한참 떨어진 곳에 있는 경우가 많다. 그래서 헤더 근처만 보지 않고 **글 전체에서 번호/메일/카톡ID 줄에 점수**(지원·문의·연락 문맥 +3, 헤더 근처 +2, 아래쪽 우선)를 매겨 고른다.
- 인스타는 "지원/DM/보내" 문맥이 있는 줄의 계정만 쓴다(소개용 `@계정`은 지원 수단이 아님).
- 링크 미리보기 카드를 지울 때 URL 줄의 앞 줄까지 지우면 바로 앞의 "지원 연락처 : 010-…" 줄이 같이 사라진다. 카드 제목/설명 줄과 도메인만 있는 줄만 지운다.

- `apply.phone`, `apply.email`, `apply.hint`(원문의 지원 방법 구간, 400자까지 줄 단위)에는 글쓴이가 지원용으로 공개한 번호·메일을 **그대로 둔다.**
- 그 밖의 필드(제목, 업무 내용, 설명 등)에서는 전화번호·카톡ID 줄을 계속 제거한다. 게하 연락처 칸(`contact_method`)은 수집 글에서 쓰지 않는다.
- 상세 페이지의 지원 버튼: 인스타 DM / 오픈채팅 / 지원폼 링크, 문자(`sms:`), 메일(`mailto:`). 다 없으면 "카페 원문 보기"만 보인다.

## 5-1. 중복 게시 규칙 (`scripts/lib/dedupe.mjs`)

끌어올리기 목적으로 같은 글을 반복해 올리는 경우가 많아서, **같은 글은 최신 1건만 노출**한다.

- 같은 작성자 + (제목 유사도 ≥ 0.6 또는 본문 유사도 ≥ 0.6) → 같은 그룹.
- 작성자가 달라도 본문 유사도 ≥ 0.85(복붙) → 같은 그룹.
- 유사도 = 한글/영문 글자만 남긴 2-gram Jaccard (본문 앞 1500자). 같은 작성자의 다른 지점 글(유사도 약 0.2)은 중복이 아니다.
- 그룹에서 가장 최신 글이 `canonical`(노출), 나머지는 중복. 가장 오래된 글 번호가 그룹 키(`firstId`)다. DB 이관 때는 이 키로 기존 행을 찾아 새로 만들지 않고 갱신(끌올)한다.
- 검수 대기 목록과 리포트도 대표 글만 대상으로 한다.
- 50건 중 중복 5건이 걸렸고 모두 같은 작성자가 하루 간격으로 다시 올린 같은 글이었다.

## 6. 수집 공고 전용 섹션 (DB 기반, 배포 사이트에 노출)

`/jobs` 필터 바 아래, 기존 공고 목록 위에 **"오늘 올라온 스탭 모집"** 섹션이 뜬다. 오늘(KST) **마지막으로 올라온** 글(새 글 + 끌올)을 최근 게시 순으로 보여주고 "오늘(10월 5일) 카페에 올라온 모집글 N건 (새 글 X건 · 끌올 Y건)"으로 표시한다. 처음 올라온 날과 다른 날 다시 올린 글에는 카드에 `끌올` 뱃지가 붙는다(`isBumped`). 정렬·전체보기 날짜 구분은 `posted_at` 기준이다. 업로드(`--days`)도 끌올 글을 포함해 `posted_at`/`repost_count`를 갱신한다. 오늘 글이 없거나 테이블이 없으면 섹션 자체를 렌더하지 않는다(`/jobs`는 깨지지 않는다).

**레이아웃 (에어비앤비식 가로 캐러셀)**: 2줄 × 한 화면 8개(데스크톱 4열, 태블릿 3열·2열, 모바일은 82% 폭 카드로 다음 카드가 살짝 보임)이고, 제목 오른쪽 위의 좌우 버튼(디자인시스템 `Button`)으로 한 화면씩 넘긴다. 옆으로 넘기면 카드 15개가 더 나와 **카드 최대 23개 + 마지막 칸은 눈에 띄는 "전체보기" 타일**(`/jobs/all_list`, 걸려 있는 필터 유지)이다. 제목 옆 `→` 버튼도 같은 곳으로 간다. 전체보기 페이지(`/jobs/all_list`)는 오늘 이전 글까지 한 그리드로 보여주고 날짜가 바뀌는 곳에만 얇은 구분선을 둔다. 섹션은 기존 사장님 공고 목록(`조건에 맞는 제주 스탭 공고`) **아래**에 놓인다. 넘길 내용이 없으면 좌우 버튼은 숨는다.

**기존 사장님 공고 섹션("조건에 맞는 제주 스탭 공고")도 같은 캐러셀**(`JobsCarousel`, `JobsMoreTile` 공통 부품)이다. 첫 화면 8개 + 15개 더 + 전체보기 타일이고, 전체보기는 `/jobs/owner_list`다. 예전 `/jobs`의 목록(20개씩 페이지 이동)이 이 페이지로 옮겨왔고, `?page=`는 `/jobs`에서 더 이상 쓰지 않는다. `getPublicJobs(searchParams, { pageSize })` 옵션으로 캐러셀은 23개를 한 번에 가져온다.

**저장 구조**: 기존 `guesthouses`/`job_posts`와 분리된 **추가 전용 테이블** `public.crawled_job_posts`(마이그레이션 `019`).
- 사장님 계정 1개당 게하 1개·게하 1개당 모집글 1개 제약과 충돌하지 않고, 소유자(`owner_id`) 개념이 필요 없다.
- 017과 같은 정책: `anon`/`authenticated` 접근을 막고(RLS) 서버 코드의 `service_role`만 읽고 쓴다.
- 같은 글 반복 게시는 `unique(source, source_group_id)`로 한 행에 모은다. 썸네일은 공개 버킷 `crawled-job-images`.

**로그인 전/후** (기존 모집글 상세 `/jobs/[slug]`와 같은 방식)
- 목록 카드는 기존 목록과 똑같이 공개(제목, 게하명·지역, 입도일·기간·근무일, 칩).
- 상세: 로그인 전에는 제목·게하명·지역·대표 이미지·급구 여부만 보이고 나머지는 "로그인 후 확인"이다. 스크롤하면 기존과 같은 **로그인 모달**이 떠서 조금만 봐도 로그인으로 이어진다.
- **연락처·지원 안내·상세 조건은 로그인 전에는 DB에서 아예 조회하지 않는다**(`getCrawledJobDetail`이 컬럼을 나눠 select). 서버 렌더 HTML에도 실리지 않는다.
- 로그인 후에는 지원 안내(번호, 메일, 카톡, 인스타, 오픈채팅, 지원폼)와 상세 조건 전체가 보인다.

**코드**: `src/lib/crawled-jobs.ts`(조회·필터), `src/components/jobs/CrawledJobsSection.tsx`(섹션), `src/app/jobs/crawled/[id]/page.tsx`(상세), `scripts/import-crawled-jobs.mjs`(업로드).

**남은 일**: 수집 글 만료/마감 처리(§7), 수집 공고에 사장님 기능(끌올·마감)은 적용하지 않는다.

## 7. 정해야 할 것

1. 수집 공고의 만료/마감 기준(예: 마지막 게시 후 N일). 지금은 "오늘 처음 올라온 글"만 노출한다.
2. 노출 위치: 지금은 기존 목록 위. 탭으로 나눌지, 목록 아래로 둘지.
3. 본문·사진을 그대로 복제하지 않고 요약 + 원문 링크로 가는 범위 (현재 상세는 파싱한 필드만 보여주고 원문 본문은 싣지 않는다).

## 8. 자동 배치 (GitHub Actions)

`.github/workflows/crawl.yml` — 한국시간 09·13·18·22시에 `crawl-naver-cafe.mjs --pages=10` → `import-crawled-jobs.mjs --days=2 --keep-existing`를 돌린다. 수동 실행은 Actions 탭의 `Run workflow`.

- **Secrets**(저장소 Settings → Secrets and variables → Actions): `NAVER_NID_AUT`, `NAVER_NID_SES`, `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`.
- **검수는 자동화하지 않는다.** 새 글은 자동 선택 썸네일과 파서 값으로 올라가고(어필 포인트 요약 없음), 이미 올라간 행은 `posted_at`/`repost_count`/원문 링크만 갱신해 수동 검수한 썸네일·요약을 덮어쓰지 않는다(`--keep-existing`). 요약·썸네일은 Claude 세션에서 채우고 `import-crawled-jobs.mjs`(옵션 없이)로 올린다.
- **쿠키 자동 연장**: 네이버가 응답마다 새 `NID_SES`를 내려주므로 `.crawl/cookie.json`에 받아 두고, 실행 사이에는 `scripts/cookie-state.mjs`가 Supabase 비공개 버킷 `crawler-state`에 보관/복원한다. Secrets 값을 새로 바꾸면(base 불일치) 저장본은 무시한다. 네이버 쪽에서 완전히 만료되면 `0004`로 실패하고 GitHub가 실패 메일을 보내니 쿠키를 다시 발급해 Secrets에 넣는다.
- `.crawl/raw`는 `actions/cache`로 이어 써서 중복/끌올 판정이 유지된다. 캐시가 비면 첫 실행이 오래 걸린다.
